# Магазин цифровых товаров — бэкенд

Покупатель берёт игровой ключ. Мы создаём заказ, ждём вебхук от платёжной системы,
идём к поставщику за кодом и отдаём код покупателю.

Всё построено вокруг одного требования: **код выдаётся ровно один раз.** Даже если вебхук
пришёл пятьдесят раз, даже если поставщик завис на середине, даже если сервис перезапустили
в момент выдачи.

Node.js + NestJS + PostgreSQL. Поднимается одной командой в Docker.

```bash
npm install
npm run verify     # поднять всё и прогнать 12 проверок
```

Отдельно: `npm run stack:up` — поднять, `npm test` — проверить, `npm run stack:reset` — начать
заново.

| что | адрес |
|---|---|
| **Документация API** | **http://localhost:3010/docs** |
| API | http://localhost:3010 |
| Поставщик A | http://localhost:4001 (документация — `/docs`) |
| Поставщик B | http://localhost:4002 (документация — `/docs`) |

## Как это работает

Заказ проходит четыре состояния:

```
created  →  paid  →  delivering  →  delivered
```

Плюс три состояния для проблем:

- `payment_failed` — оплата не прошла;
- `out_of_stock` — оплата прошла, но кода нет в наличии;
- `delivery_failed` — оплата прошла, но поставщики не смогли выдать код.

Последние два — **не ошибка, а пауза**. Заказ остаётся в базе, фоновая задача возвращается
к нему позже и доводит до `delivered`, когда товар появится.

### Оплата

Вебхук от платёжной системы может прийти много раз и в любом порядке. Поэтому:

1. Событие пишется в таблицу `payment_events`, где `event_id` — первичный ключ. Если такой
   `event_id` уже есть, обработка сразу заканчивается: это повтор доставки.
2. Заказ переводится в `paid` запросом `UPDATE ... WHERE status = 'created'`. Сколько бы
   запросов ни пришло одновременно, база пропустит ровно один.

Если вебхук пришёл раньше, чем создан заказ, событие сохраняется и применяется позже, когда
заказ появится. Отвечаем `200`, а не `404`, иначе платёжка будет слать его вечно.

### Выдача кода

Поставщиков два: основной A и резервный B. У каждой попытки свой номер:

```
req_ord_00123_A_1
```

Этот номер отправляется поставщику. Если отправить его повторно, поставщик обязан вернуть
**тот же самый код**, а не выдать новый.

## Три важных момента

### 1. Таймаут — это не отказ

Самое главное во всей задаче.

> Поставщик мог успеть выдать код, а ответ просто не дошёл.

Поэтому при таймауте мы **не идём к резервному поставщику**. Попытка получает статус
`unknown`, и единственный способ узнать правду — повторить запрос с тем же номером.

Если бы мы сразу переключились на B, то A выдал бы код, B выдал бы второй, и один ключ пропал
бы навсегда. К резервному поставщику переходим только после понятного отказа — когда он прямо
ответил «ошибка» или «нет в наличии», то есть точно ничего не выдал.

Порядок действий внутри выдачи принципиален:

1. выйти сразу, если код у заказа уже есть;
2. занять заказ переводом в `delivering`;
3. **разобраться со всеми незакрытыми попытками** — до любых новых запросов;
4. и только потом делать новую попытку, сначала к A, затем к B.

Если повтор снова упирается в таймаут, счётчик растёт, заказ остаётся в `delivering`, следующий
заход сделает фоновая задача. Когда лимит исчерпан, попытка помечается как требующая ручного
разбора — с отдельной записью в логе, а не молчаливым отказом.

### 2. Идемпотентность живёт в базе, а не в коде

Ни один критичный переход не написан как «прочитать → проверить → записать». Каждый — это
условный `UPDATE`, где условие и есть проверка:

```sql
UPDATE orders SET status = 'paid' WHERE id = $1 AND status = 'created'
```

Из 50 одновременных вебхуков ровно один получит `rowCount = 1`, остальные 49 увидят ноль и
ничего не сделают. Postgres сам выстраивает их в очередь на блокировке строки — приложению
не нужно ничего координировать.

Сверху этого работают уникальные индексы, которые страхуют уже от ошибок в самом коде:

| индекс | что запрещает |
|---|---|
| `orders (delivered_code)` | один код в двух заказах |
| `delivery_attempts (order_id) WHERE status = 'ok'` | две успешные выдачи по заказу |
| `ledger_entries (order_id, kind, ref, ...)` | задвоение проводки при повторе |

Даже если в логике появится ошибка, база не даст выдать дважды.

### 3. Журнал денег всегда сходится

Двойная запись, две проводки:

- оплата: `Dr gateway_receivable / Cr deferred_revenue`
- выдача: `Dr deferred_revenue / Cr revenue`

Проверка — нулевой баланс по каждой валюте:

```sql
SELECT currency_code,
       SUM(CASE direction WHEN 'debit' THEN amount_minor ELSE -amount_minor END)
FROM ledger_entries GROUP BY currency_code;
```

Полезное следствие: остаток на счёте `deferred_revenue` **математически равен** сумме заказов
«оплачен, но не выдан». Денежная и операционная сверки сходятся к одному числу, и отчёт
`/admin/reconciliation` проверяет именно это равенство.

## Как проверить руками

### 50 одновременных вебхуков

```bash
node scripts/pay.mjs --sku KEY-CS2-PRIME --concurrency 50
```

Скрипт создаёт заказ и шлёт 50 вебхуков разом:

```
200:applied              1     ← только одно событие сработало
200:ignored_not_pending  49    ← остальные ничего не изменили
final order: { status: 'delivered', code: 'YPLV-QK2Z-IUS5' }
counters: { successful_attempts: 1, delivery_issued_postings: 2 }
```

### Повтор одного события

```bash
node scripts/pay.mjs --concurrency 20 --same-event
```

Один раз `applied`, девятнадцать раз `duplicate`.

### Поставщик A упал → выдаёт B

```bash
curl -X POST localhost:4001/_control -H 'content-type: application/json' -d '{"hard_down":true}'
node scripts/pay.mjs --sku GIFT-PSN-1000
curl -X POST localhost:4001/_control -H 'content-type: application/json' -d '{"hard_down":false}'
```

Код придёт от B, попытки к A останутся со статусом `failed`.

### Поставщик выдал код и завис

```bash
curl -X POST localhost:4001/_control -H 'content-type: application/json' -d '{"issue_then_hang":true}'
curl -X POST localhost:4002/_control -H 'content-type: application/json' -d '{"hard_down":true}'
node scripts/pay.mjs --sku KEY-EFT
```

Заказ дойдёт до `delivered` с тем самым кодом, который A записал до зависания. Проверить, что
поставщик выдал ровно один код:

```bash
curl localhost:4001/_state/order/<order_id>
```

### Сверка денег

```bash
curl -s localhost:3010/admin/reconciliation
```

Показывает оплаченные, но не выданные заказы, выданные без оплаты и баланс журнала.

### Настройка поставщиков

У каждого поставщика есть ручка `POST /_control`, меняющая поведение на лету:

```bash
curl -X POST localhost:4001/_control -H 'content-type: application/json' -d '{
  "failure_rate": 0.4,
  "timeout_rate": 0.3,
  "latency_ms": 100,
  "hard_down": false,
  "force_out_of_stock": false,
  "issue_then_hang": false
}'
```

`POST /_control` — частичное обновление: переданные поля меняются, остальные сохраняются.
Вернуть заглушку в исходное состояние одной командой:

```bash
curl -X POST localhost:4001/_control/reset
```

Пополнить остаток: `POST /_control/restock` с телом `{"sku": "KEY-EFT", "count": 10}`.

## API

Интерактивная документация — **`/docs`** на самом сервисе: http://localhost:3010/docs.
Там можно не только прочитать, но и вызвать любую ручку прямо из браузера. При развёртывании
она поедет вместе с приложением и будет доступна по домену, отдельно её публиковать не нужно.
Машиночитаемая спецификация OpenAPI 3.0 лежит рядом: `/docs-json` — её можно скормить Postman,
Insomnia или генератору клиентов.

У каждой заглушки поставщика своя документация: http://localhost:4001/docs и
http://localhost:4002/docs — включая ручки управления сбоями.

Ниже — краткий список того же самого.

**Покупателю**

| метод | путь | что делает |
|---|---|---|
| GET | `/products` | список товаров с остатками |
| GET | `/products/:sku` | карточка товара |
| POST | `/orders` | создать заказ: `{"sku": "KEY-GTA5"}` |
| GET | `/orders/:id` | статус заказа и код, если выдан |

**Платёжной системе**

| метод | путь | что делает |
|---|---|---|
| POST | `/webhooks/payment` | приём вебхука об оплате |

**Поддержке**

| метод | путь | что делает |
|---|---|---|
| GET | `/admin/reconciliation` | сверка: что оплачено, но не выдано |
| GET | `/admin/orders/:id/audit` | вся история заказа: события, попытки, проводки |
| POST | `/admin/orders/:id/retry-delivery` | добить заказ вручную |
| POST | `/admin/recovery/run` | прогнать восстановление прямо сейчас |

## Где что лежит

```
src/
  orders/          заказы и их состояния
  payments/        приём вебхуков оплаты
  delivery/        выдача кода, работа с поставщиками
  ledger/          журнал денежных движений
  reconciliation/  сверка и восстановление зависших заказов
  catalog/         витрина товаров
  supplier/        заглушка поставщика (одна на двоих, A и B)

  queue/           очередь фоновых задач
  database/        подключение к базе, миграции, тестовые данные
  money/           работа с суммами и валютами
  logging/         логи
```

Если читать код впервые, начните с двух файлов:

- `src/payments/payments.service.ts` — как гасится поток одинаковых вебхуков;
- `src/delivery/delivery.service.ts` — как обрабатывается зависший поставщик.

Рядом с `src/`:

```
migrations/   схема базы ядра, применяется автоматически при старте
seed/         каталог товаров и пул ключей — файлы из задания как есть
test/         состязательные сценарии из раздела «Критерии приёмки»
scripts/      pay.mjs — эмулятор платёжной системы, он же генератор гонок
              wait-for-api.mjs — ожидание готовности стека для npm run stack:up
```

`scripts/pay.mjs` вынесен отдельно, потому что задание требует эмулировать оплату «тем же
скриптом, что и для проверки гонок»: им можно и просто оплатить заказ, и обстрелять один заказ
полусотней параллельных вебхуков.

## Схема данных

Восемь таблиц. Половина работы по надёжности сделана не кодом, а ограничениями базы.

### Деньги

```
currencies
  code       char(3)   ISO 4217
  exponent   smallint  знаков после запятой: RUB = 2, JPY = 0, KWD = 3
  symbol     text
```

Все суммы — целые числа в минорных единицах (копейках) плюс код валюты. Масштаб хранится
**один раз на валюту**, а не в каждой строке с суммой.

Причин две. Масштаб — свойство валюты, и в строке он допускает несогласованность вроде `RUB`
со scale 3, которую не поймает ни один констрейнт. И главное: разный масштаб в строках ломает
проверку журнала — нельзя сложить 500 со scale 2 и 500 со scale 0, а это сложение и есть
основная проверка консистентности денег.

Добавить новую валюту — одна строка данных и ноль изменений в коде.

**Единицы на границе.** В контракте вебхука приходит `"amount": 500` при цене товара 500 ₽,
то есть мажорные единицы. Перевод в минорные делается явно при приёме, сравнение с ценой
заказа строгое. Без этого либо все платежи отвергались бы, либо принималась бы оплата в сто
раз меньше цены.

### Каталог

```
products
  sku            text      первичный ключ
  price_minor    bigint
  currency_code  char(3)
  type           text      topup | key | subscription | giftcard
  is_active      boolean
  popularity     integer   порядок на витрине
  stock_count    integer   денормализованный остаток
```

Один индекс обслуживает весь горячий запрос витрины:

```sql
CREATE INDEX products_showcase_idx
  ON products (type, popularity DESC, sku DESC)
  INCLUDE (name, price_minor, currency_code, stock_count)
  WHERE is_active;
```

Фактический план на 5012 товаров (`GET /products/explain?type=key`):

```
Limit  (cost=0.28..8.46 rows=24 width=52) (actual time=0.131..0.133 rows=24 loops=1)
  Buffers: shared hit=3
  ->  Index Only Scan using products_showcase_idx on products
        Index Cond: (type = 'key'::text)
        Heap Fetches: 0
        Buffers: shared hit=3
Execution Time: 0.151 ms
```

`Heap Fetches: 0` и три страницы буфера — запрос вообще не касается таблицы. Работают три вещи:
нужные колонки лежат в индексе через `INCLUDE`; условие `WHERE is_active` делает индекс
маленьким, и он целиком помещается в память; порядок сортировки совпадает с порядком индекса,
поэтому сортировки нет.

Одна тонкость: `Index Only Scan` даёт нулевые `Heap Fetches` только когда заполнена карта
видимости, а её обновляет `VACUUM`, а не `ANALYZE`. Поэтому сид заканчивается командой
`VACUUM ANALYZE products` — иначе на свежей базе тот же запрос ходил бы в таблицу за каждой
строкой (`Heap Fetches: 24`) до первого прохода autovacuum.

Остаток `stock_count` денормализован и обновляется фоновой синхронизацией с поставщиков —
витрина никогда не считает `COUNT(*)` по ключам и не ходит в интеграции. Пагинация keyset
(`(popularity, sku) < (:p, :s)`), а не `OFFSET`: стоимость страницы не растёт с глубиной.

### Заказы

```
orders
  id                     text     'ord_00123', может задаваться клиентом
  sku, price_minor, currency_code
  status                 text     created | paid | delivering | delivered |
                                  payment_failed | out_of_stock | delivery_failed
  delivered_code         text     выданный код
  delivery_attempt_no    integer  счётчик попыток выдачи
  last_payment_event_at  timestamptz  для разбора вебхуков не по порядку
  idempotency_key        text
```

```sql
CREATE UNIQUE INDEX ON orders (delivered_code) WHERE delivered_code IS NOT NULL;
CREATE UNIQUE INDEX ON orders (idempotency_key) WHERE idempotency_key IS NOT NULL;
CREATE INDEX ON orders (status, updated_at)
  WHERE status IN ('paid','delivering','out_of_stock','delivery_failed');
```

Первый физически запрещает одному коду попасть в два заказа. Второй делает повторное создание
заказа безопасным. Третий — маленький партиальный индекс, по которому фоновая задача находит
зависшие заказы, не сканируя всю таблицу.

### События оплаты

```
payment_events
  event_id       text  ПЕРВИЧНЫЙ КЛЮЧ — здесь живёт дедупликация
  order_id       text  БЕЗ внешнего ключа
  status         text  paid | failed
  amount_minor, currency_code
  occurred_at    timestamptz  время из payload, определяет порядок
  applied_at     timestamptz  NULL = ещё не применено
  apply_result   text  applied | duplicate | order_missing | ignored_stale | ...
  payload        jsonb
```

Отсутствие внешнего ключа на `order_id` — сознательное решение, и именно оно позволяет принять
вебхук, пришедший раньше заказа.

### Попытки выдачи

```
delivery_attempts
  request_id       text  УНИКАЛЬНЫЙ, детерминированный: req_{order}_{provider}_{attempt}
  order_id, provider, attempt_no
  status           text  in_flight | ok | failed | unknown
  code             text
  reconcile_count  integer
  error_reason     text
```

Запись создаётся **до** HTTP-вызова: если процесс умрёт в момент запроса, факт попытки уже
сохранён.

### Журнал денежных движений

```
ledger_entries
  txn_id         uuid   одна проводка = две строки
  order_id
  account        text   gateway_receivable | deferred_revenue | revenue
  direction      text   debit | credit
  amount_minor   bigint
  currency_code  char(3)
  kind           text   payment_captured | delivery_issued
  ref            text   event_id или request_id
```

Проводка никогда не смешивает валюты — все строки одного `txn_id` в одной валюте. Будущая
конвертация оформляется отдельной проводкой через счёт `fx_conversion`, а не пересчётом сумм
внутри существующих строк.

### Служебные таблицы

```
supplier_stock   остатки по поставщикам, из них считается products.stock_count
jobs             очередь фоновых задач
schedules        периодические задачи и время следующего запуска
```

**У заглушек поставщиков базы нет.** Они изображают внешнюю систему, поэтому не имеют доступа
ни к базе ядра, ни к его миграциям: пул кодов, журнал выданного и настройки сбоев живут
в памяти процесса. Ядро узнаёт их остатки единственным законным способом — запросом `GET /stock`,
результат складывается в свою таблицу `supplier_stock`.

Побочный эффект: перезапуск заглушки возвращает выданные коды обратно в пул, чего настоящий
поставщик не делает. Если после такого перезапуска код попытается уйти во второй заказ,
уникальный индекс `orders (delivered_code)` не даст этого сделать — попытка получит
`code_already_used`, и выдача пойдёт следующим кодом.

Поэтому тесты рассчитаны на чистый стек: `npm run verify` сам делает сброс перед прогоном.
Если перезапустить заглушки руками, не сбрасывая базу, часть кодов окажется конфликтной —
система это переживёт (заказы уйдут в восстановимое состояние и доедут до `delivered`),
но прогон будет дольше. Перед `npm test` в такой ситуации лучше сделать `npm run stack:reset`.

**Про пул ключей.** Все 50 ключей из задания загружены в заглушки (30 поставщику A, 20 — B)
и выдаются первыми. Сверх них генерируется запас случайных кодов, иначе пул кончился бы после
двух прогонов тестов. Отключается переменной `SUPPLIER_EXTRA_KEYS_PER_SKU=0`.

## Остальные решения

### Вебхуки не по порядку

Три случая, все покрыты тестами.

**Событие пришло раньше заказа.** Сохраняется с `applied_at = NULL`, ответ `200`. При создании
заказа ставится задача, которая применяет накопленные события; та же выборка периодически
подметается фоном.

**Опоздавший `failed` после `paid`.** Событие старше последнего применённого отбрасывается как
`ignored_stale`; более новое упирается в `WHERE status = 'created'` и ничего не меняет.
Успешная оплата не откатывается.

**`paid` после `failed`.** Деньги важнее схемы: подтверждённая оплата, пришедшая позже отказа,
поднимает заказ из `payment_failed` обратно в `paid`. Сознательное расширение жизненного цикла
из задания — иначе реально оплаченный заказ навсегда остался бы отказным.

### Два разных замка

Гонки бывают двух видов, и каждый закрывается своим механизмом:

- **advisory-лок** `pg_try_advisory_lock('deliver:<order_id>')` на выделенном соединении —
  не даёт двум исполнителям (фоновая задача и ручной повтор) войти в выдачу одновременно;
- **условный переход** в `delivering` — не даёт войти повторно после сбоя раньше, чем истечёт
  порог зависания.

Лок именно на уровне сессии, а не транзакции: транзакционный потребовал бы держать транзакцию
открытой всё время запросов к поставщику, чего делать нельзя.

### Очередь в Postgres вместо брокера

Своя очередь (`jobs` + `FOR UPDATE SKIP LOCKED`) выбрана ради одного свойства: задача на выдачу
ставится **в той же транзакции**, что и перевод заказа в `paid`. Не бывает состояния «статус
сменился, а задача потерялась» или наоборот. С внешним брокером эту щель пришлось бы закрывать
отдельной таблицей и релеем.

Изначально в плане был pg-boss, но он работает через собственный пул соединений и поставить
задачу в чужой транзакции не позволяет — ради чего всё и затевалось.

Активные задачи дедуплицируются партиальным уникальным индексом, зависшие в `running`
возвращаются в `pending` по таймауту блокировки, повторы идут с растущим интервалом.

### Восстановление без отдельной логики

Фоновых задач четыре: применить осиротевшие события, разобраться с незакрытыми попытками,
добить зависшие заказы, обновить остатки. Ни одна не содержит своей бизнес-логики — все
вызывают ту же функцию выдачи, что и основной путь.

Поэтому «безопасно довести зависший заказ» безопасно по построению, а не потому, что мы
аккуратно написали ещё одну ветку.

Повторы разведены по времени растущим интервалом от номера попытки, чтобы заказ без товара не
дёргал поставщиков каждые две секунды. Автоматические повторы конечны; ручной
`POST /admin/orders/:id/retry-delivery` работает всегда.

### Поведение при отказе инфраструктуры

Пул соединений подписан на событие `error`: падение базы логируется как `database.pool_error`,
но процесс не умирает. Вебхук в этот момент отвечает `500` — по контракту платёжная система
повторит доставку, и событие не теряется. Фоновый воркер ловит сбой тика (`worker.tick_failed`)
и продолжает опрашивать очередь; после возвращения базы работа идёт дальше без вмешательства.

Проверено вживую: `docker compose stop postgres` → вебхук отдаёт 500, сервис жив; после
`start postgres` тот же `event_id` применяется и заказ доходит до `delivered`. Отдельно
проверено `kill -9` контейнера API прямо во время запроса к поставщику: незакрытая попытка
осталась в `unknown`, после подъёма реконсилирована тем же `request_id`, выдача ровно одна.

### Логи

Структурный JSON, сквозной `trace_id` от приёма вебхука до выдачи кода:

```json
{"event":"payment.captured","trace_id":"55cc27...","order_id":"ord_f3b7","status_from":"created","status_to":"paid","amount_minor":129000}
{"event":"supplier.call","trace_id":"55cc27...","provider":"A","request_id":"req_ord_f3b7_A_1","outcome":"ok","duration_ms":3}
{"event":"delivery.delivered","trace_id":"55cc27...","provider":"A","status_from":"delivering","status_to":"delivered","code":"07E8-C644-40FD"}
```

Весь путь одного платежа поднимается по одному значению `trace_id`.

## Что сделано по этапам

| этап | сделано | где смотреть |
|---|---|---|
| 1. Ядро API | заказ по SKU, заказ по id, вебхук оплаты, авто-выдача, переходы статусов | `orders/`, `payments/`, `delivery/` |
| 2. Exactly-once | дедупликация по `event_id`, условные переходы, три уникальных индекса | `payments/payments.service.ts` |
| 3. Интеграции | два поставщика, таймауты, повторы с растущим интервалом, fallback A→B, ловушка таймаута | `delivery/` |
| 4. Сверка и восстановление | JSON-логи со сквозным `trace_id`, `/admin/reconciliation`, четыре фоновые задачи, журнал двойной записи | `reconciliation/`, `ledger/` |
| 5. Каталог | 5000+ товаров, покрывающий партиальный индекс, keyset-пагинация, план запроса | `catalog/`, `migrations/001_init.sql` |

Критерии приёмки — каждый закрыт отдельным тестом:

| критерий | тест |
|---|---|
| 50 параллельных вебхуков — одна выдача | `npm run test:race` |
| повтор `event_id` ничего не меняет | `npm run test:duplicate` |
| вебхук вне порядка или раньше заказа | `npm run test:out-of-order` |
| таймаут поставщика, который выдал код | `npm run test:timeout-trap` |
| A недоступен, fallback на B | `npm run test:fallback` |
| пустой остаток, восстановимое состояние | `npm run test:out-of-stock` |

### Сознательные отклонения

**`payment_failed` не финальный.** В задании этот статус помечен как финальный. У нас из него
разрешён один переход — обратно в `paid`, и только если событие об оплате новее события об
отказе. Причина: платёжные системы доставляют вебхуки не по порядку, и при доставке `failed`
раньше `paid` реально оплаченный заказ навсегда остался бы отказным. Остальные переходы
из `payment_failed` запрещены.

**Расширенный пул ключей.** Все 50 ключей из задания на месте и выдаются первыми; сверх них
генерируется запас, чтобы тесты воспроизводились многократно. Отключается через
`SUPPLIER_EXTRA_KEYS_PER_SKU=0`.

**Справочник валют из одной строки.** Пересчёт валют делать не требовалось, поэтому в
справочнике только RUB. Таблица нужна не ради мультивалютности, а ради `exponent` — без него
нельзя корректно перевести `"amount": 500` из вебхука в копейки.

## Как масштабировать

**Чтение.** Витрина — кэш в Redis на 5–10 секунд со сбросом по событию синхронизации остатков,
плюс реплики на чтение для каталога. Заказы и журналы остаются на основной базе.

**Запись.** Воркеры выдачи масштабируются горизонтально как есть: `SKIP LOCKED` и лок по
`order_id` уже дают безопасный параллелизм. При росте нагрузки — раскладывать воркеры по хэшу
`order_id`, чтобы уменьшить конкуренцию за лок.

**Журналы.** `payment_events` и `delivery_attempts` растут линейно по трафику. Партиционирование
по месяцам, холодные партиции в архив. Сверка работает по горячей партиции.

**Очередь.** Postgres как брокер спокойно держит тысячи задач в секунду. За этим порогом
очередь выносится в отдельный брокер, а транзакционность сохраняется явной outbox-таблицей
с релеем — тем же приёмом, который сейчас получается бесплатно.

**Остатки.** Сейчас `stock_count` пересчитывается целиком. При десятках тысяч товаров —
инкрементальное обновление по событию выдачи плюс периодическая полная сверка.

**Поставщики.** Circuit breaker на клиенте: после нескольких отказов подряд поставщик временно
исключается из ротации, что убирает лишние таймауты из горячего пути.

## Сколько заняло

Около 4 часов: проектирование схемы и алгоритмов — примерно 40 минут, реализация — около двух
часов, состязательные тесты и отладка — час, документация — остаток.

Самое дорогое место оказалось не там, где ожидалось. Логика идемпотентности заработала почти
сразу, а время ушло на две гонки, которые видны только под нагрузкой:

- форсированное восстановление пускало двух исполнителей в выдачу одновременно — закрылось
  advisory-локом;
- счётчик попыток жёг лимит на фоновых повторах и уводил восстановимый `out_of_stock`
  в `delivery_failed` — закрылось растущим интервалом вместо жёсткого лимита.
